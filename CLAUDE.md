# dirigo-bid-system

Commercial drywall bidding tool for Dirigo Drywall. Estimating model is **assembly-and-area based, not crew-hours based** — don't propose or add hourly-productivity concepts. Deployed at `ddbidding.netlify.app` (repo: `edahms01/dd-bidding`).

## Architecture — read this before touching rendering

**As of A2, every page in this app is React** — `src/` owns the shell (header, left nav, tab bar) and all ten pages (Project, Conditions, Rates, Assemblies, Walls, Ceilings, Output, Agent Recommendation, History, Dashboard), plus the finalize modal (shell-owned, reachable from both Tab 7 and Tab 8). `js/*.js`'s classic scripts are still real and load-bearing underneath — orchestration (`runCalculation()`, `_launchBidAgent()`, draft lifecycle, autosave, calculator/history-analytics/agent — all untouched, "no business logic changes" per the plan) still lives there, called from React via `window.*` bridges (`src/state/bridges.js`) exactly the way `window.goto` has worked since the spike. `LegacyPage.jsx` and the classic-script render functions it used to wrap (`renderOutput()`, `renderAgentTab()`/`_renderAgentResult()`, `renderDashboard()`, etc.) are dead now, not yet deleted — the final cleanup pass (see the A2 section below) removes them once verified nothing still calls them. **Read "A2: React migration — hybrid coexistence" further down before touching state, navigation, or any page's rendering** — the mechanism is load-bearing and non-obvious; changes that look safe in isolation (e.g. "just add a `<script type=module>`", "just read `window.hasUnsavedChanges`", "just dispatch and read the DOM back synchronously", or "just call addAsm()/addWall()/addCeil() once at boot like always") broke things more than once during the migration, on nearly every page it touched.

The rest of this section describes the vanilla layer, still accurate for every not-yet-converted page:

The app is vanilla HTML/CSS/JS, loaded as **classic (non-module) `<script>` tags**, in this exact order (`index.html`, near the closing `</body>`):

```
js/autosave.js → js/drafts.js → js/state.js → js/calculator.js →
js/history-analytics.js → js/history.js → js/rate-templates.js →
js/agent.js → js/forms.js → js/tabs.js → js/ui.js → data/seed.js
```

Order matters — later files call functions defined in earlier ones via plain global scope (classic scripts all share one `window`). There is **no bundler-managed dependency graph** for this code yet (see Build tooling below for what *is* bundled).

**State lives in the DOM, not in memory.** `collectFormData()` (`js/state.js`) rebuilds a full bid object by reading input values back out by element ID/position on demand — there's no central store. `populateForm()` (`js/forms.js`) writes a plain object back into the DOM. The one real in-memory state is a near-empty `STATE` object (`js/state.js`) holding just the confidence level. This is a known, deliberate limitation — see "Phase A migration" below.

**Rendering is no longer split at all — both groups this section used to describe are empty now.** Neither the "static markup in `index.html`, mutated via targeted DOM writes" group (Project, Conditions, Rates, Assemblies, Walls, Ceilings) nor the `innerHTML`-replace-on-every-render group (History, Dashboard, Agent Recommendation, the Output sub-panels — `js/ui.js`'s `renderHistory`/`renderDashboard`/`renderAgentTab`/`_renderAgentResult`/`renderOutput`) has any pages left in it; all ten converted to React over the course of A2. The functions themselves are dead code now, not deleted yet — see the A2 section below.

**Module boundary that must survive any future rendering rewrite**: `calculator.js` and `history-analytics.js` are pure, already unit-tested — no DOM access. `drafts.js` and `history.js` are storage/network. `agent.js` is the agent invocation. `netlify/functions/*` is the backend. These stay as plain modules regardless of what owns rendering.

## A2: React migration — hybrid coexistence

**Two sources of truth exist simultaneously, and that's intentional, not a bug to "fix" by converting everything to Context.** Converted pages (Rates, History) read/write through `src/state/store.jsx`'s `useReducer`+Context. Every not-yet-converted page still reads/writes through the original `collectFormData()`/`populateForm()` DOM-scan (`js/state.js`, `js/forms.js`). Both feed the *same* draft object in `dirigo_drafts` — `collectFormData()` still reads real `<input>.value` regardless of whether React or vanilla JS rendered that input, so this works without an adapter layer for reads. Writes are the part that needed care — see below.

**`LegacyPage` (`src/pages/LegacyPage.jsx`)** is the coexistence wrapper for every unconverted page. Each page's exact original markup lives in an inert `<template id="legacy-tpl-{id}">` in `index.html`. `LegacyPage` clones that template's content into its own DOM once, via a `ref`, in a `useEffect` with an empty dependency array — then never touches those children again. Its own JSX never describes children (`<div ref={...} id={...} />`, nothing inside), so React's reconciler has nothing to diff there on any future re-render, no matter what triggered it. Verified directly, not assumed: typing in Rates (real React state, causes a re-render) leaves an already-populated Conditions page's `innerHTML` byte-for-byte identical. **Do not add children to `LegacyPage`'s JSX** — that reintroduces exactly the bug this pattern avoids.

### Converting a page — standard checklist, not a Rates/History-specific writeup

The Rates/History conversion surfaced two classes of bug that are **structural to how every remaining page was written**, not incidental to those two pages — expect to hit both again on Project/Conditions/Assemblies/Walls/Ceilings/Output/Agent, not as a coincidence but because every one of them assumes the same things Rates and History used to.

1. **Boot-ordering: anything that used to run at classic-script-load time or on `DOMContentLoaded` and touches that page's DOM must move to `'dirigo:shell-ready'` instead.** `js/forms.js`'s old INIT section (`addAsm()`/`addWall()`/`addCeil()` default rows, the `.workflow-area` input/change listener that actually drives autosave, `_initDraftsAndResume()`'s draft restore) assumed the page's real DOM already existed — true when every page was static HTML present the instant the parser reached it, **not true** once a page's markup is cloned in asynchronously by `LegacyPage`'s post-mount effect. `DOMContentLoaded` does not fix this: module scripts run before it fires, but React's `useEffect` is scheduled for after paint — a race against it, not a guarantee of ordering. Reproduced directly on this spike, not theorized: `addAsm()` threw on a null `#asm-body`, and separately, silently, the autosave listener was never attached at all. Fixed once, generally, with `AppShell` dispatching `'dirigo:shell-ready'` after every `LegacyPage` child's mount effect has run (children's effects fire before a parent's, in the same commit) — `forms.js`'s `_initApp()` listens for that instead of `DOMContentLoaded`. This mechanism doesn't need to change as more pages convert; **audit whatever page-specific init code the next page has for the same assumption** before assuming it's fine.
2. **Element IDs must stay unique across the whole document once a page converts, because every not-yet-converted page is now always mounted simultaneously, not just the active one.** That was already true before this spike (all pages have always stayed mounted, just via CSS class toggling) — the risk is new only in the sense that a page being actively rewritten is an easy moment to accidentally introduce a collision without noticing, since only one page is usually on screen during manual testing. Checked directly before writing the Plastering/External-wall regression spec: Rates' own crude totals bar (`#t-tot`) and Output's real direct-cost total don't collide only because Output's total happens to carry no `id` at all — not because anything enforces this. When converting a page, grep the *whole* app for any `id` the new component renders, not just that page's old markup.
3. **A React-controlled input's DOM value updates during React's commit, without firing a native `input`/`change` event.** Anything that used to rely on that event (the `.workflow-area` autosave listener, `calc()`'s old `oninput` triggers) will not fire just because reducer state changed — see `window.__hydrateRates()` and the immediate-save-after-template-load fix below for two concrete cases this already bit.
4. **`dispatch()` is batched/async — any classic-script function that dispatches and then synchronously reads the DOM back in the same tick will read stale values.** This is not one call site's bug, it's a standing constraint on `populateForm()` (`js/forms.js`) as a whole, found by auditing every `collectFormData()` call site after the first instance of it surfaced, per Eric's explicit request — check the same way on any future page, don't wait to be asked twice. Two real, reproduced instances, not a hypothetical:
   - `resetFormFields()` dispatches `RESET_BID` to blank the React-owned sections, but its caller, `_createAndActivateBlankDraft()`, calls `collectFormData()` *immediately after*, in the same call stack, before React has flushed anything to the DOM. A dispatch-only fix saved the **old draft's data** into the supposedly-blank new draft — worse than the display-only bug it was fixing.
   - `data/seed.js`'s `loadSeedData()` calls `populateForm()` (dispatches `__hydrateRates` etc.) and then, still synchronously, calls `runCalculation()` — which calls `collectFormData()`. Tab 7 showed **"$0"** immediately after clicking "Load seed data," self-correcting only once something else (a later tab visit) re-triggered a calculation after React had actually flushed. Genuinely user-visible, not a test-only artifact — reproduced by clicking through it, not just by a spec.

   Both are fixed the same way, and `populateForm()` now applies this uniformly across every section (Project/Conditions/Intelligence/Rates), not just the two call sites that happened to get caught: **every section does the plain `set(id, val)` DOM writes *and* calls its `window.__hydrateX` bridge — unconditionally, not as an if/else fallback pair.** The plain writes make any synchronous read (right after `populateForm()`/`resetFormFields()` returns) correct immediately; the dispatch makes the *next* unrelated re-render correct too, so it doesn't silently revert the plain writes (checklist item 3). Both write the identical final value, so there's no flicker to a *wrong* value in either direction — just two paths converging on one answer. Apply this same "do both, always" shape to any future page's hydration, not an if/else that picks one.
5. **Any reducer action that hydrates a whole section from an external object must merge onto current state, recursively, never replace it outright — this is a standing rule, not a one-off patch for old data.** Found converting Project, but the reasoning is general: `legacy-migration.spec.js`'s pre-drafts fixture (`dirigo_current_bid`, predating the `scope` field) has a `project` object with no `scope` key at all. A wholesale replace left `state.bid.project.scope` `undefined`, and `ProjectPage.jsx`'s `p.scope.includes(label)` threw on the very next render — a real crash, not a display glitch. The schema is going to keep growing (the post-Phase-G assembly-extensibility work will add fields; whatever comes after that will too), and old/partial data — a legacy migration, an imported file, a rate template saved before a field existed — will keep lacking newer fields as it does. A single-level `{...current, ...incoming}` only half-fixes this: it still wholesale-replaces any *nested* object (`rates.finish`, `.stud`, `.board`) the same way. `store.jsx` now has one `mergeDeep(base, incoming)` helper — recurses into nested plain objects, replaces arrays wholesale (a list doesn't merge field-by-field), a key *present* in `incoming` wins at any depth, a key *absent* from it falls back to `base` — and both `LOAD_SECTION` and `LOAD_RATES` go through it. **Any future hydration action must too — never add a new one with a bare object-spread replace.**
6. **A classic-script global that used to be a page's source of truth becomes stale everywhere the instant that page converts, not just at the one call site you're looking at.** `STATE.conf` (`js/state.js`) was fixed for `collectFormData()`'s confidence field when Conditions converted, but two *other* direct reads of `STATE.conf` — `runCalculation()`'s and `submitBid()`'s markup-contingency pre-fill (`js/ui.js`) — were missed in the same pass, because they're a different call site, not because the reasoning didn't apply. Selecting a confidence level in the browser no longer touches `STATE.conf` at all (`ConditionsPage.jsx` dispatches straight into the reducer), so both silently pre-filled contingency to 0% regardless of what the estimator actually picked — reproduced directly (select High confidence, run a calculation, contingency comes back 0 instead of 4), not assumed. Fixed with one shared `_currentConfidence()` helper (`js/ui.js`) using the same `window.__getConfidence()`-with-`STATE.conf`-fallback pattern `collectFormData()` already used, so there's one accessor instead of the rule being reimplemented per call site. **When a page converts, grep the whole app for direct reads of whatever classic-script global used to hold its state — a partial fix (the first call site found) is worse than no fix, because it looks complete.**

**Two more, specific to converting a page whose content is a variable-length list of rows (Assemblies; will recur on Walls/Ceilings), found building `AssembliesPage.jsx`** — a genuinely new category of hazard, not a rediscovery of the scalar-page patterns above:

7. **Manually rebuilding a list-container's children from classic-script code fights React's ownership of that same list — the scalar "plain write + dispatch" trick from item 4 does NOT extend to lists.** For a single `<input>`'s value, an external write and React's own re-render can coexist because they can converge on the same value with no visible conflict. For a *list* of `<tr>` children, React's reconciliation diffs against its own internal fiber tree, not against whatever the live DOM currently contains — externally appending/replacing children there produces broken or duplicated rows, not just a stale read. Two real, reproduced instances, not hypothetical:
   - `_initApp()` (`js/forms.js`) unconditionally called `addAsm()` at boot, appending a rogue extra `<tr>` into `#asm-body` — harmless when that element was still classic-script-owned, actively broken once `AssembliesPage.jsx` also renders into it via `.map()`. Found by reproducing it directly: a debug read of `#asm-body`'s `innerHTML` right after boot showed the `addAsm()`-generated row's telltale inline `style="width:...px"` and `onchange="updateAsmId(...)"` attributes — markup `AssembliesPage.jsx` never produces — sitting where React's own row should have been. Fixed by removing that call (the page's own `initialState.bid.assemblies` already establishes the one-blank-row-on-boot invariant `addAsm()` used to be responsible for); `addWall()`/`addCeil()` stay, unconverted pages still need them.
   - `populateForm()`'s/`resetFormFields()`'s old row-rebuild code (`asmBody.innerHTML = ''; asmCount = 0; rows.forEach(() => addAsm())`) had to be replaced outright with a dispatch-only bridge (`window.__hydrateAssemblies`), not kept alongside it the way Project/Conditions/Rates keep their old `set()` calls — the old code is now the *fallback*, used only when the bridge isn't registered, never run alongside it.
8. **The synchronous-read-after-hydrate hazard (checklist item 4) still applies to lists, but the scalar fix (plain write + dispatch) can't solve it there — use `flushSync` instead.** `loadSeedData()` still calls `populateForm()` (hydrates rows) and then synchronously `runCalculation()` (reads them back via `collectFormData()`'s DOM query) in the same tick, same shape that caused Tab 7's Rates "$0" flash. Since a list can't use the dual-write trick (item 7), `window.__hydrateAssemblies`/`window.__hydrateWalls`/`window.__hydrateCeilings`/`window.__resetBidState` (`bridges.js`) wrap their dispatch in React DOM's `flushSync()`, which forces React to apply the update *synchronously* before the bridge function returns, instead of the default batched/async commit — so a caller reading the DOM immediately after sees the freshly-hydrated rows. Verified directly on Assemblies, then again on Walls/Ceilings: loading seed data and reading the Output total within 50ms of the load call, before any other tab visit could correct a stale read, produced the right total immediately, not a flash of `$0` that then corrected itself. **Scoping caution, not a general-purpose fix: reach for `flushSync` only for this specific class of problem (a classic-script caller that hydrates a React-owned *list* and then synchronously reads the DOM back in the same tick).** It forces React out of its normal batching, which has real cost — overusing it defeats the point of batching and tends to paper over a design problem rather than fix one. If a future stale-read finding seems to need it in a third place, that's a signal to re-examine why, not to reach for another `flushSync` call by reflex.

9. **A top-level `window.X = ...` assignment in `js/ui.js` must be guarded, because Vitest actually imports this file — found converting Output, not assumed.** `tests/unit/ui.test.js` imports `js/ui.js` under Vitest's plain `'node'` environment (no `window` at all) specifically to unit-test `escapeHtml()` — the file's header already documents one existing guard for exactly this (`document.addEventListener('keydown', ...)` wrapped in `typeof document !== 'undefined'`). Adding `window.__getLastAgentResult = () => _lastAgentResult;` at module scope, unguarded, broke that import immediately (`ReferenceError: window is not defined`) — caught by `npm test`, not assumed clean. Every new top-level (not inside a function) `window.X = ...` in this file needs the same `typeof window !== 'undefined'` guard as the existing `document` one; a bridge assignment *inside* a function body is fine either way, since it only runs when called.
10. **Same "a stale global read gets found once, not everywhere" shape as `STATE.conf` (item 6) — this time on `_lastAgentResult`.** `submitBid()`'s failure panel has always had a "Try again" button reading `_lastAgentResult` (`js/ui.js`, a top-level `let`) — safe as a bare identifier in the original inline `onclick="..."` attribute (classic-script global scope sees it fine), but a React `onClick` handler runs in module scope and can't see it that way at all; `window._lastAgentResult` is also wrong, for the same reason `window.hasUnsavedChanges` was (checklist bridges list) — a `let` doesn't become a `window` property. Fixed with `window.__getLastAgentResult()`, same accessor shape as `__getHasUnsavedChanges`/`__getConfidence`. Caught while porting this one button, not by a full re-audit this time — **worth a real audit (grep every bare classic-script-global reference an onClick handler needs) before Agent converts**, since Agent's own markup reads several more of these (`_selectedBidOption`, `_agentLoading`, etc.) that haven't been checked yet.
11. **A multi-branch classic-script render function's *least obvious* branch is the one a bridge port drops — write out every branch before assuming three cover it.** `renderAgentTab()` (`js/ui.js`) has four branches, not three: cached result wins outright; else loading wins; else an *empty* state — **except** a fourth, easy-to-miss branch sits between loading and empty: if `_agentLoading` is false and nothing's cached yet but `_agentResult` (a fresh, not-yet-cached result) is already available, it falls through to showing *that* — and caching it as `_lastAgentResult` in the process, via `_renderAgentResult()`'s own assignment. The bridge's first draft only ever dispatched `_lastAgentResult`, silently losing that fourth branch — which is also the *first* real render of every agent run (nothing is cached yet the very first time a result arrives), so it broke on the most common path, not an edge case. Reproduced by two real, distinct spec failures, not caught by re-reading: `agent-history-fallback.spec.js` (the notice never appeared — the page fell through to the empty state instead of the real result) and `draft-switch-no-contamination.spec.js` (both tabs showed the empty state, not each draft's own result). Fixed by reconstructing the same fallback chain in the bridge itself (`resultToShow = _lastAgentResult || (!_agentLoading ? _agentResult : null)`), including the caching side effect. **When porting any render function with more than two branches, write out the full branch table from the original before writing the bridge — don't reconstruct it from memory of "the important cases."**

**React `key` for a row list must be a stable per-row *identity*, generated once and never reused — not array position, and not reset on every hydration the way some of a row's other bookkeeping fields legitimately are.** Each assembly row's fields are deliberately left *uncontrolled* (`defaultValue`, not `value`+`onChange` — matching `collectFormData()`'s original DOM-query-by-position read exactly, and avoiding a dispatch on every keystroke for fields nothing else needs to react to live). Uncontrolled inputs only apply `defaultValue` on first mount, never again — so if the key is index-based (or, just as broken, reset to a position-based number on every hydration), deleting a middle row or switching drafts causes React to *reuse* a DOM node for what is now different row data instead of unmounting it, and the reused node's uncontrolled inputs keep showing the *previous* occupant's stale typed values. Reproduced directly twice, not assumed: deleting a middle row initially looked fine in isolation, but switching from a draft with a typed Notes value to a fresh "New Bid" draft leaked that same value into the new draft's blank row, because both hydrations reset their id-auto-generation counter (`_num`) to 1-indexed position — and the first draft of this fix mistakenly reused `_num` as the React key too. Fixed with a *separate* field, `_key` (`store.jsx`'s `freshRowKey()`) — a plain, session-wide, never-reset counter, distinct from `_num` (which correctly *does* reset per hydration, since it drives the `updateAsmId()`-ported id-auto-generation side effect, not reconciliation).

**`updateAsmId()`'s category→auto-ID side effect** (js/forms.js) — determines whether changing an assembly row's Category select should also flip its Type ID between the `W{n}`/`C{n}` auto-generated forms, unless the user has already typed a custom ID — is ported almost verbatim into `AssemblyRow`'s `onChange` handler in `AssembliesPage.jsx`, operating on a plain DOM ref to the sibling ID input, not modeled as reducer state at all. It's a pure same-row DOM side effect nothing else in the app needs to observe; routing it through dispatch/re-render would be new complexity for no behavior gain.

**No pixel widths in generated markup, decided empirically for Assemblies (an A2 acceptance criterion, not deferred to Phase D):** built and visually verified `<table>` + a page-level `<colgroup>` (column widths defined once, not duplicated per generated row — the actual defect the criterion targets) rather than the CSS-Grid-row pattern `RatesPage`'s `.ftable`/`.fth`/`.frow` uses. Rates' grid pattern fits a narrow 3-column layout; Assemblies is 11 columns wide with a genuine mix of narrow (selects) and wide (notes) content, and native `<table>` semantics/auto-sizing read better there once actually built and screenshotted, not just assumed by analogy to Rates. This was never actually spiked — the A2 spike covered Rates and History, neither of which has add/delete rows — so treat it as a real, if now-answered, open question, not a rediscovery of a proven pattern. Walls/Ceilings should follow the same `<table>` + `<colgroup>` approach unless something about their narrower column set argues otherwise.

**`window` bridges (`src/state/bridges.js`)** let unconverted classic-script code and inline `onclick="..."` attributes keep working without knowing anything changed underneath them — same pattern already used for the Preflight's module-export deferral, reused here for navigation:
- `window.goto(id)` — replaces `js/tabs.js`'s `goto()`. Dispatches the tab change into the shared reducer and still fires the per-tab legacy side effects (`runCalculation()` on Output, `renderAgentTab()` on Agent) for pages that haven't converted. `'conditions'`/`'rates'` cases are gone — `ConditionsPage.jsx`/`RatesPage.jsx` each run their own on-become-active side effect via their own `useEffect` now.
- `window.showHistory()` / `window.showDashboard()` — replace `js/tabs.js`'s same-named functions. History no longer calls the legacy `renderHistory()` at all (see below); Dashboard still does.
- `window.toggleNav()` — replaces `js/tabs.js`'s `toggleNav()`, same `dirigo_nav_collapsed` localStorage key.
- `window.__hydrateRates(rates, rateEscalation)` / `window.__hydrateProject(project)` / `window.__hydrateConditions(conditions)` / `window.__hydrateIntelligence(intelligence)` — the fix for a real hazard: these pages' inputs are React-controlled now, so a direct external `.value` write gets silently overwritten on the next re-render, since React never learns the DOM changed out from under it. But `populateForm()` (`js/forms.js`) calls the bridge **alongside** the old `set()`-based DOM writes, not instead of them — see checklist item 4 above for why the writes are still required too. `__hydrateProject`/`__hydrateConditions`/`__hydrateIntelligence` share one generic `LOAD_SECTION` reducer action; `__hydrateRates` drives `LOAD_RATES`. Both actions (`store.jsx`) go through the same `mergeDeep()` helper rather than replacing a section outright — see checklist item 5.
- `window.__resetBidState()` — the fix for a second, more serious hazard on top of the one above: `resetFormFields()` (`js/forms.js`) still does its original plain `el.value = ''` writes for Project/Conditions/Intelligence/Rates (required — see checklist item 4 above, `_createAndActivateBlankDraft()` reads the DOM back synchronously right after), but *also* calls this bridge so the reducer's copy is blanked too, or the next re-render restores the old values into the DOM the user is looking at. Dispatches `RESET_BID` (`store.jsx`), which resets `state.bid` to a deep clone of `initialState.bid` in one shot — this has never been a "reset just one section" operation, so one action covers all four at once.
- `window.__getConfidence()` — the read-direction counterpart to the hydrate bridges: `STATE.conf` (`js/state.js`) is folded into the reducer now (`conditions.confidence`), so `collectFormData()` reads the live value through this accessor instead, registered by `ConditionsPage.jsx` via the separately-exported `registerConfidenceReader()` (not part of `registerBridges()` — needs `ConditionsPage`'s own live state, not just a `dispatch` reference). `STATE.conf` itself stays as a fallback for non-browser/pre-mount contexts.
- `window.__getHasUnsavedChanges()` — `hasUnsavedChanges` (`js/forms.js`) is a top-level `let`, which — unlike a `function` declaration — does **not** become a `window` property in a classic script; `window.hasUnsavedChanges` from React code was always `undefined`. This one-line accessor is the fix. Found running the suite, not assumed.
- `window.toggleUpdate(bid_id)` — `HistoryPage.jsx` reimplements the Bid History "Update" row as real React state (`openUpdateId`), but existing specs call `toggleUpdate(bid_id)` directly rather than clicking the button. Bridged the same way.
- `window.__hydrateAssemblies(rows)` / `window.__hydrateWalls(rows)` / `window.__hydrateCeilings(rows)` — replace `populateForm()`'s old `xBody.innerHTML=''; rows.forEach(() => addX())` rebuilds (`store.jsx`'s `LOAD_ASSEMBLY_ROWS`/`LOAD_WALL_ROWS`/`LOAD_CEILING_ROWS`). Dispatch-only (not the scalar sections' plain-write-plus-dispatch shape — see checklist item 7), each wrapped in React DOM's `flushSync()` so the DOM is already updated by the time the bridge function returns (checklist item 8).
- `window.__hydrateMarkup(markupInputs)` — Markup (overhead/contingency/profit) joined the reducer as part of converting Output (it's a section *within* that page in the original markup, never its own tab); same generic `LOAD_SECTION` action Project/Conditions/Intelligence share. Also called mid-calculation: `runCalculation()`'s/`submitBid()`'s contingency-from-confidence pre-fill logic (`js/ui.js`) writes `#markup-contingency`'s DOM value directly *and* calls `window.__hydrateMarkup({ contingencyPct })` — same dual-write shape as checklist item 4, needed because that field is React-controlled now (`OutputPage.jsx`) and the direct write alone would be silently reverted the next time anything re-renders the page. `LOAD_SECTION`'s merge semantics update just the one field passed, leaving `overheadPct`/`profitPct` alone.
- `window.__renderOutput(output)` — replaces `renderOutput()`'s (`js/ui.js`) old direct `#output-phase3`/`#output-bid.innerHTML` writes with a dispatch into `state.ui.output` (`store.jsx`'s `RENDER_OUTPUT`). No `flushSync` — nothing reads the DOM synchronously right after `runCalculation()` calls this, so plain dispatch is correct and preferred (checklist item 8's scoping caution).
- `window.__setSubmitResult(result)` — replaces `submitBid()`'s (`js/ui.js`) old direct `#output-bid.innerHTML` writes for the post-finalize success/failure panel, dispatching into `state.ui.submitResult` instead. Deliberately preserves the known wrong-tab bug exactly — verified directly, not just left alone on faith (see "Known pre-existing quirks" below).
- `window.__getLastAgentResult()` — see checklist item 10. Same accessor shape as `__getHasUnsavedChanges`/`__getConfidence`, for the same reason: a classic-script `let` a React event handler needs to read.
- `window.__renderAgentTab(snapshot)` — replaces `renderAgentTab()`'s/`_renderAgentResult()`'s (`js/ui.js`) old innerHTML branch. Both functions still run from every call site they always did and still own reading `_lastAgentResult`/`_agentLoading`/`_agentResult`/`_agentHistoryUnavailable` and writing `_lastAgentResult` — they just dispatch a snapshot now instead of building HTML. See checklist item 11 for the branch this bridge got wrong on the first attempt (a fresh, not-yet-cached `_agentResult` falling through to display-and-cache) and how it was found.
- `window.__resetAgentCache()` — replaces `_resetAgentCache()`'s (`js/ui.js`) direct global resets for the React-owned copy, called alongside them (not instead) on every draft switch/blank-draft activation.
- `window.__resetBidState()` also now wraps its `RESET_BID` dispatch in `flushSync()`, for the same reason — it's the only thing that clears the assemblies table now that `resetFormFields()` no longer does its own `#asm-body` rebuild.

**Known pre-existing quirks the React port had to replicate exactly, not fix:**
- **Plastering and External wall rates are never costed — this is a real product gap, not cosmetic dead UI. See `docs/dirigo-ux-decisions.md` §9.9 for the full severity writeup and `tests/e2e/rates-plaster-extwall-not-costed.spec.js` (inverted spec, same pattern as the finalize-persistence defect) for the pinned regression.** Both real `$/SF` inputs (`#rate-plaster`/`#rate-extwall`), both look identical to every other priced Rates field, neither reaches a bid total — verified in the code, not assumed: `calculator.js` never reads either rate, there's no assembly/wall/ceiling category that could carry a quantity for them, and `conditions.exteriorExposure` (the flag that reads as though it should gate the External-wall rate) is captured but also never read by `calculator.js`. `RatesPage.jsx` renders both as plain uncontrolled inputs, matching this exactly rather than wiring them to anything. **Not scheduled for a fix** — needs a product decision on how these should connect to a quantity, which is Eric's call, not a code call.
- `RatesPage`'s totals bar (`TotalsBar`/`recomputeTotals`) replicates `calc()`'s exact mechanism — a live DOM class-query summing every `.L`/`.M`/`.X`-classed input's raw `.value` — rather than deriving purely from reducer state. This was a deliberate choice, not an oversight: deriving from state alone would silently exclude the two orphan fields above (they contribute to the display today; a pure-state derivation would have "fixed" that without being asked to).
- Saving a rate template used to go through `collectFormData()`, whose `num()` helper parses every field via `parseFloat` (NaN → 0) before persisting — `"5.00"` typed by a user was always saved and reloaded as the number `5`. `RatesPage`'s reducer state holds the *raw typed string* (a controlled input has to, or it fights the user mid-keystroke), so saving it directly would persist `"5.00"` verbatim — a real, caught-by-the-suite behavior difference. `numify()` in `RatesPage.jsx` replicates `num()`'s exact rule before every template save.
- Loading a rate template used to do an **immediate, non-debounced draft save** (`applyRateTemplate()`'s own comment explains why: so a reload right after loading a template can't lose it to a race against the normal 700ms autosave debounce). Dispatching into the reducer alone doesn't trigger that — React sets a controlled input's DOM value directly during its commit, without firing a native `input`/`change` event, so the `.workflow-area` delegated listener never sees it. `RatesPage.jsx`'s `handleLoadTemplate()` schedules a call to `window._autosave()` (the existing, non-debounced save function) via a one-render-delayed effect, so it runs after React has actually committed the new values to the DOM — calling it any earlier would save the *previous* values.
- **The finalize-panel wrong-tab bug (`submitBid()`'s success/failure panel always targets `#output-bid`, physically on Tab 7, regardless of which tab was active when finalize ran — see Known follow-ups below) is preserved exactly, verified with a real test, not assumed to survive by construction.** This mattered specifically because the mechanism changed even though the behavior isn't supposed to: the panel used to be a direct `innerHTML` write into a static DOM element; it's now a dispatch into `OutputPage`'s own `state.ui.submitResult`, rendered conditionally by a component that also renders the normal Phase 4 breakdown in that same slot. It would have been easy for the panel to "naturally" end up visible whenever *any* page renders it, accidentally fixing the bug as a side effect of the new architecture — which the plan explicitly says not to do here. Verified with a test that finalizes from Tab 8 (inducing a failure) and asserts `#page-output` does **not** have the `active` class while `#page-agent` does, i.e. the panel exists in the DOM but isn't the page the user is looking at — not just "a panel appeared somewhere." Also confirmed the panel is cleared by the next calculation exactly as before: navigating to Tab 7 re-triggers `runCalculation()` (`window.goto()`'s existing `output` case), which dispatches a fresh `RENDER_OUTPUT` and clears `submitResult` — so revisiting Tab 7 after a finalize-from-Tab-8 shows the normal breakdown, never the confirmation, the same non-obvious (and unfixed) consequence of the bug the original app already had.
- **Tab 8's cached agent result wins even over a fresh calculation already in flight — not a simplification, the real original behavior, and load-bearing for checklist item 11's fix.** If a user has a cached result, clicks Recalculate, and switches to Tab 8 before the new agent call resolves, `renderAgentTab()`'s cache-hit branch shows the *stale, pre-recalculation* result — `_lastAgentResult` isn't cleared until a draft switch (`_resetAgentCache()`), not on every recalculation. `AgentPage.jsx` replicates this exactly (`cachedResult` wins regardless of `loading` in the branch order) rather than "fixing" it to show a loading state, which would have been an easy, plausible-looking, unapproved behavior change.

## Build tooling

**Vite** is standing up production build tooling (`vite.config.mjs`), landed as part of the Phase A React migration's Preflight work — **the app itself is still fully vanilla; only the build pipeline changed.** `package.json`'s `"type": "commonjs"` is deliberately unchanged (Netlify Functions and the classic script tags both depend on that; see `docs/preflight-report.md` for why `type="module"` isn't compatible with this app as structured).

**`vite.config.mjs` has one non-obvious plugin** (`copy-classic-script-sources`): `vite build` refuses to bundle classic `<script src>` tags *and* silently omits the files they reference from `dist/` — a plain `vite build` here produces a build that looks successful but 404s on every `js/*.js` file at runtime. The plugin copies `js/` and `data/` into `dist/` after build, with a build-time assertion that fails loudly if any expected file goes missing. **This plugin must be deleted once Phase A's React migration (A2) converts `js/*.js` to real bundled module imports** — at that point it would start shipping untransformed duplicate files alongside the bundled output, silently. Tracked as an explicit A2 checklist item (see Phase A section below for where the authoritative plan lives).

`npm test` = Vitest (`vitest.config.mjs`, `environment: 'node'`, `tests/unit/**/*.test.js`). `npm run test:e2e` = Playwright (`playwright.config.mjs`, `tests/e2e/`, single worker — bid history lives in one shared Netlify Blobs store, `fullyParallel: false` because specs share `localStorage`).

## Netlify config

`netlify.toml` now has an explicit `[build]` block (`command = "vite build"`, `publish = "dist"`, `functions = "netlify/functions"`) and an explicit `[dev]` block (`command = "npx vite --port 5173"`, `targetPort = 5173`) — without the `[dev]` block, Netlify's framework auto-detection misreads `package.json`'s scripts and tries to run `npm run test` as the dev command instead of starting Vite. Without this flag, production and every deploy preview fail to build at all (confirmed: this took down the first real deploy-preview build attempt for this exact reason). Rollback path, verified: reverting the merge commit that introduced this config (`git revert -m 1 <merge-sha>`) restores `publish = "."` with no build command — the pre-Phase-A production config — with a clean, empty diff against the last commit before that merge. Confirmed by diffing, not just asserted.
